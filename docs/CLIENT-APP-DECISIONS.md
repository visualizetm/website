# Client app: decisions

The job is docs/CLIENT-APP-PROMPT.md. Each call made without asking, with the rule that decided it.

1. (1) The dev switch is a path prefix, the way the admin's is: on localhost the client app lives under /app (APP_BASE, appPath() and isAppPath() in src/lib/adminPaths.js), and the pre-paint script treats /app like the app host. Plainer than a query flag, and the audits reach it on the preview server.
2. (1) Maintenance mode stays off the app host as it does the admin: a client's own panel is not the public site.
3. (1) The app host's CSP is the public site's own policy (images from any https host, media and connect only from Cloudinary, the pinned inline script, frame-ancestors 'none'), plus Cache-Control no-store. It is the strictest block the portal and the planner run under today; nothing they load needs more.
4. (1) Until the data doors move to the cookie (milestone 3), the app host serves /c/:token and /planner/:token with the existing pages, so the host works from its first deploy and nothing breaks in between.
5. (1) The app host's / no longer preloads the marketing Home chunk (the pre-paint script skips it on the app host).
6. (2) A lockout is counted on consecutive wrong codes: the 5th locks fifteen minutes, a try during that lock is refused unread and not counted, the 6th to 9th after it are counted without a new lock, the 10th locks until Rob resets it. Plainer than a lock on every multiple of five.
7. (2) The lock is told (423 with the minutes, or hard) only to someone holding the setup link or the right code. By phone or email a wrong code during a lock is the same 401 as any other miss, so locking a phone out never tells a stranger it belongs to a client.
8. (2) A hard lock does not sign out devices already in: the lock guards the door, and a stranger locking the code must not lock the real client out of a phone already signed in. Rob's Reset code does sign every device out.
9. (2) Rob's push on the hard lock uses category client (Client activity), the closest existing one: it is about one client's account, like an approval or an idea.
10. (2) Two clients sharing one phone or email both get the plain 401 by that identifier; each still signs in from their own link. Safer than guessing which one.
11. (2) The CRM's list read and the backup carry portal.code as its status only (set, setAt, locked, lockedUntil, fails), never the hash or the salt: four digits behind a leaked hash are ten thousand guesses away. Restore is out of scope, so a backup never needs the hash.
12. (2) Reset code lives on a new admin route, client-app (POST reset-code), behind route(); milestone 5 adds Rob's read only previews there. It ships in milestone 2 because the guard proof needs it.
13. (2) The code door's set step needs both fours (code and again) on the server too, not only on the screen.
14. (3) Milestones 3 and 4 are pushed together. Moving the data doors to the cookie without the screens that set and ask for a code would leave every client on the live site with no way in between the two pushes. Each is still its own commit, in order.
15. (3) The old link redirects (milestone 5 in the prompt) ship with milestone 3 for the same reason: once a token stops reading data, an old visualizestudio.org link must land on the app host's code door. They are permanent: false (a 307 on Vercel, which browsers do not cache), not a 308: the prompt asks for a redirect that can be undone, and a 308 is cached as permanent.
16. (3) The data doors take the lead only from the cookie on every host, not only the app host: the cookie is host only on app.visualizeclients.com, so a data read anywhere else is the 401 too. Less code, and nothing reads a client by token anywhere.
17. (3) A deleted record under a valid session answers the door's own 404, as a deleted record always did (sessionLead returns it with deleted: true and each door decides), and /api/app/me reads it as signed out.
18. (3) The PIN door (action pin) and the unlock token it mints stay on the server, unasked by the app: a signed in session is already unlocked, so the GET no longer reads ?unlock=. portal.pin stays on the record (additive schema).
19. (3) The tests that read with a bare token sign in through scripts/client-signin.mjs, which goes through the real code door (it sets a code on a client with none, else signs in with it) and, for a link the door does not open (a planner switched off), writes a code the door's way so the doors' own 404 rules can still be checked. Counts: planner-endpoint 136 to 138, planner-alerts 67 to 68, portal 249 to 250, security 1264 to 1291, portal-guard-proof 123 to 124 cuts; dst, planner-board, links and coverage-push do not read with a token and are unchanged.
20. (3) Checks that said an unknown token is the 404 now say it is the 401 sign in (with no session the token is nothing, before any lookup); the "same bytes" checks keep their strength (one body for every miss). "A revoked token is the same 404" became "a regenerated link opens no code door, and Reset code ends the session on the very next call". The PIN unlock checks now verify the session: its signature (a tampered cookie reads nothing), Reset code ending it, and the registry still locking a sensitive card for anyone not unlocked.
21. (3) GET /api/app/token answers step 'in' when the device is already signed in as the client the link belongs to, so a link from the portal's planner card (or a text Rob sends again) goes straight in instead of asking for the code.
22. (4) The Add to Home Screen card is its own screen, shown once right after the code is set (not in a browser already standalone), dismissed for good on the device (vz_app_a2hs). The portal's own older hint is off inside the app so the client never sees two.
23. (4) The panel's settings are a /settings screen of the client app, reached from a Settings text link under the portal's cards and at the bottom of the planner's Alerts sheet; Sign out is the text link at its bottom. It holds who is signed in, the pings line and the code line; the switches stay where they were (the portal's Notifications card, the planner's bell).
24. (4) Signed out, /api/app/me also answers Rob's own number from Settings (textRob, digits only) for the "Forgot it? Text me" sms: link; it is Rob's business number, already on every portal's Contact card, and nothing about a client.
25. (4) The code field is a password field with the number pad (inputMode numeric, pattern [0-9]*), autocomplete new-password on the set step and current-password on sign in, with the phone or email as the username field, so a password manager can offer to save it.
26. (4) The audit fixtures emulate the session with a vz_client cookie naming the fixture's link (appSignIn in scripts/audit-fixtures.mjs); the real cookie is signed and HttpOnly, which a mock cannot be. The portal's three PIN states (locked, the PIN sheet, a wrong PIN) no longer exist in the app, so their audit entries became the app's door states (sign in, the kept identifier, a wrong code, a setup link, a locked link, set, a weak code, the second four, the Home Screen card, an expired link, Settings).
27. (4) An audit state that ends on a click moves the mouse away before it is measured, as eleven existing entries do: the primary button's hover fill is docs/TOKENS.md's recorded 4.27:1 exception, and the resting state is what is audited.
28. (5) CLIENT_APP_BASE (https://app.visualizeclients.com) and PUBLIC_SITE (https://visualizestudio.org) sit beside PORTAL_URL_BASE in src/shared/portalModules.js and its mirror; every client URL is built from them. The setup link (portalUrl, the planner's link on Rob's buttons) is the app host plus the token; portalPath, the way back the planner, concepts and review doors answer, is the app's home with no token; the portal's planner card is the app's own /planner; the concepts and review cards are absolute links to the public site, where those pages still live.
29. (5) An email carries the setup link (with the token) until the client has set a code, then the app itself with no token (clientAppLink). The setup link is the one token an email may carry, and before a code exists it is the way in.
30. (5) Push deep links open the app host: the planner's at /planner (?review=1, ?post=, ?tab=ideas), the portal's at /. A device registered on visualizestudio.org gets the same absolute URL; public/sw.js already opens whatever URL the push names (a window it can drive, else a new one), so it needed no change.
31. (5) Rob's previews are a small page of their own on the admin host (/preview/portal/:id and /preview/planner/:id, /admin/preview/... on localhost), opened in a new tab from the portal sheet (Preview as the client) and the planner (Preview as), outside the shell, so the back tree is untouched. The route is GET /api/admin/client-app?view=&id= behind route() and the admin cookie; it calls the same read the client's door calls (portalRead, plannerRead) with preview: true, which stamps nothing. No client cookie is made for Rob.
32. (5) Read only means no write control drawn: the planner has no bell, no approve or change bar, no Post it and no idea composer; on the portal each card a client writes from (approvals, reorder, a site change, pings) shows its title and one line instead, and no tap is counted. Navigation (tabs, Review mode, a post) still works.
33. (5) The portal sheet's PIN section is now Their code: one line (Code: set Nov 24, Code: not set yet, Locked, 10 wrong tries in red, or the minutes of a short lock) and Reset code behind a confirm, which posts once to the admin route and updates the record in place (leadOps.applyLocal). Open as the client became Preview as the client: the setup link would ask Rob for the client's own code. Make a new link now says that phones already signed in stay signed in.
