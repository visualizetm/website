# VISUALIZE ADMIN, ARCHITECTURE (as of 3.1.0, Site Prompt 5, 2026-09-07)

The admin CRM at admin.visualizeclients.com and the marketing site at
visualizestudio.org share one Vite build. This file describes the app as it
is now. History lives in reports/PROMPT-NN-REPORT.md; operations live in
docs/RUNBOOK.md.

## The CRM revamp, steps 1 to 7, in one place

Seven steps rebuilt the pipeline on main; each is described once here and the details sit beside the data they touch below.

1. Stages and decline. Stage is `normalizeStage` on the stage field: triage, lead, booked, deal, client, nurture, declined (won and lost remain on old records). A declined record carries the reason, is never revived by an import, and comes back through Bring back. Leads has Open, Declined and Nurture pools. ClickUp is gone.
2. The next action. Every lead and project carries one `nextAction`, computed by one rule set (src/lib/nextAction.js, mirrored in api/_lib/nextAction.js), recomputed by the shared patch helpers and repaired by the daily cron; a manual action is never overwritten. Next up (the first screen) reads it and nothing else.
3. Dial lists. A list of leads with a target and a window, the system list Callbacks due, the ListPicker everywhere a lead is, and the Call Console running a list with the outcome rule on the same write.
4. Triage, the score, nurture and quick capture. Every new lead lands in triage, sorted by a score computed from one rule set; Keep, Later (nurture) and Decline move it; the cron brings nurture back; Capture a lead takes a handle, a number or a name.
5. Deals and invoices. A booked lead becomes a deal with nine checkpoints; the board on /deals sits a card in the column of its newest tick; invoices are one shape on deals and projects (projects.schedule[] is gone), entered and marked by hand; the first Mark paid is the one conversion to client and project.
6. The four branded emails through Zapier catch hooks, sent from the record with the stamps on success; ESLint in the audit.
7. Follow up rules in the daily cron (api/_lib/rules.js, once per record per condition, counted in health.crons.daily.rules), the client-side project actions (revision round, deliver, retainer pitch) and the dated delivery checklist, the Projects screen at /projects, and the phone shell: the thumb tabs are Next up, Lists, Call, Deals and More; the More sheet lists Triage, Leads, Clients, Projects, Orders, Reviews, Calendar, Submissions, Recently Deleted, Concepts, Declined, Settings, Landing and Design. Nothing is computer only: every editor renders at every width, and New project, Start a retainer and Fill from filters are pages (src/pages/AdminProjectNew.jsx at /clients/:id/projects/new and /projects/new, src/pages/AdminListFill.jsx at /lists/:id/fill).

## Client docs (docs job)

Rob keeps a client's briefs, call notes, contracts, delivery notes and brand notes as docs. Admin only: there is no public link and no public endpoint reads the collection.

- **Data.** A `docs` collection (backed up with the rest): `{ leadId, projectId, type (brief, call-notes, contract, delivery, brand-notes, general), title, pinned, blocks, text (the block text, for search), blockCount, deleted, deletedAt, createdAt, updatedAt }`. A saved template is the same document with `template: true` and no client; the built in templates' hidden and order live in settings `doc-templates`. A created or deleted doc is also logged on the client (`docLog`, capped at 100, $push with $slice) and History shows it as Created doc and Deleted doc, never an autosave.
- **Blocks are data, never HTML.** `src/shared/docBlocks.js` (mirrored byte for byte in `api/_lib/docBlocks.js`, asserted by `scripts/docs-test.mjs`) is the schema: heading, subheading, text, bulleted, numbered, checklist, quote, divider, link, image and reference blocks; text blocks hold `runs` of `{ t, b, i, a }` so bold, italic and a link are the only marks. `sanitizeBlocks()` drops an unknown type, caps every string, the runs and the block count (400), keeps only http and https links, and an image only on https at res.cloudinary.com. Nothing that draws or edits a doc writes HTML (the security test scans for the sinks).
- **References.** A reference block is `{ kind (concept, project, task, invoice, file), id }` plus a cached name. The route refuses a new one that is not the same client's record; one already stored stays, so a deleted task never blocks the autosave. The chip reads the record live (`src/lib/docRefs.js`: its name and status from what the shell holds) and a record that is gone says "No longer there".
- **Routes.** `/clients/:id/docs` (one client's docs, grouped by type, a focused screen), `/docs` (every client, the More page's Docs row and the sidebar's Clients group), `/docs/:id` (the editor, a focused screen on a phone, a routed page on a computer, also where a saved template is edited). The shell loads the list once (`src/lib/useDocs.js`: meta only, no blocks) and hands `docsApi` to the screens through the shell context; the client's Docs card, All docs, the More count, global search and Recently Deleted read that one list. `src/lib/workspace.js` `docsStatus` is the card's count and rows.
- **The editor** (`src/pages/AdminDoc.jsx`, `src/components/docs/`): `DocEditor` holds the blocks and the operations (`src/lib/docEdit.js`, pure and tested), `RichText` is a contentEditable that holds only runs (text nodes in strong, em and a built with createElement; paste is plain text), `TitleField` is the big title (a contentEditable because the app keeps every form control at 16px on a phone). The formatting bar sits above the keyboard on a phone (it follows `visualViewport`) and is a sticky strip on a computer.
- **Autosave** (`src/lib/docSave.js`, framework free, tested on a fake clock): about a second after the last key, one request at a time, text typed during a request goes in the next; a failed save keeps the text, says "Not saved, retrying" and retries 2, 4, 8, 15 seconds; a 4xx is "Not saved" and not retried; Back saves first; text that could not be saved stays in memory when the editor closes and the next open of the doc takes it over.
- **Templates** (`src/lib/docTemplates.js`): six built in (Blank, Project brief, Call notes, Contract, Delivery notes, Brand notes) plus the saved ones. Creating a doc fills the `[tokens]` this client can answer (name, contact person, package, price, payment plan, project start date, revision rounds, Rob's name) as plain text and leaves every other one as a visible placeholder. The contract's house rules (2 revision rounds, extra rounds $50 design and $75 web, the 50 percent deposit, files only at full payment) come from `src/shared/pricing.js` and are always filled. Make a task on a call note's follow up line writes through the task system (`addTask` and `checklistsPatch`); a doc's checklist never becomes a task by itself.
- **Print and copy.** Export is Copy as text (`docPlainText`) and Print or save as PDF: a portal at the end of body holds the doc alone, a print stylesheet hides the app and sets black on white; the browser's print sheet does the rest.

## Navigation

The nav revamp (reports/NAV-REVAMP-REPORT.md): one nav config
(src/shell/nav.js) drives the sidebar, the tab bar, the More page, the
command bar and the top bar title. The sidebar shows one workspace at a
time through the WorkspaceSwitcher (Pipeline: Dashboard, Triage, Leads,
Call Console, Lists, Deals, Calendar; Clients: Dashboard, Clients,
Projects, Docs, Planner, Tasks, with the Studio rows under it), follows
the route (workspaceOf) and remembers the pick; Analytics is pinned above
both, Settings, Design, the account and Collapse below. Every screen's
header is the PageHeader the top bar renders (breadcrumb workspace then
page, title, Back, actions) with the OverviewStrip beside the search
(meetings in 7 days, due today, overdue), which a phone shows on one line
atop the home. Every list plus detail screen keeps its list in a
CollapsiblePane (a rail of initials when collapsed, remembered per screen,
independent of the sidebar). Moved routes keep working: /?open= redirects
to /tasks?open=, `analytics` and `dashboard` both name the home.

src/shell/nav-history.js is the one navigation model (Back, done once). Every open of a record, an editor, a setup page, a sheet sized page or a console mode is a history push, never a replace; the entry's state carries the request (`open { section, id, intent, mode }`, `create`, `preset`) and the `origin` captured from the screen that leaves at the moment of the push (path, search, scrollTop, panelScrollTop, selectedId, filters, view, tab), plus `idx`, the entry's depth. AdminApp reads the requests off the entry (no in-memory openReq, createReq or presetReq), `useSelection(section)` gives a screen its selected id, `open()` (a push on the same path) and `close()` (history back), `useScreenOrigin` registers what a screen holds beyond path and search, and `useRestore` hands the origin back to the screen that returns: it reapplies the filters, the search, the view and the tab, then restores the scroll and lights the row (`[data-row-id]`, `.nav-restored`) once the data is present, never on a skeleton. `useBack()` drives the top bar's Back on phone and computer and the record's inline Back; it is null at a section root, and a record reached by a deep link (?open=, ?submission=, a push notification) with no origin shows Back to its section root. Back is history.back(), so the browser's back and the phone's edge swipe run the same popstate path and Forward re-opens the record. The Call Console's queue, room and summary are entries with the builder as the root; the Settings tabs on a phone and Design opened from Settings are entries; the editors and the setup pages keep their leave guard on Back. Sheets and modals are not history entries. scripts/back-test.mjs walks it at 390 and 1280.

### Chrome modes (CRM mobile revamp)

`src/shell/chrome.js` is the one rule for what surrounds a phone screen, a function of the history entry. An entry that carries an `open` or a `create` request, or whose path is deeper than a section root, is **focused**; everything else is **tabs**. The shell writes the mode to `data-chrome` on `.sh-root`.

- tabs (a section root, a list, More): the tab bar is shown and the top bar offers Search, Quick add and Notifications. Tab labels are 11px.
- focused (a record opened from a list, an editor and its steps, a setup page, the Call Console's room, queue and summary, a create form, Settings groups): the tab bar is hidden (its height animates to 0, it is `inert`), the screen gets the space, the home indicator inset moves to the content, and the top bar is Back, the title and only what the screen declares through `useTopBar({ title, back, actions })`. Controls are replaced between modes, never added to; the clusters fade in on a change (`--v-dur-*`, collapsed under Reduce motion).
- A bar pinned above the tab bar (SaveBar) reads `--v-tabbar-now`, which is 0 while the tab bar is hidden.
- Desktop (768 and up) has no tab bar and its top bar is unchanged.
- scripts/chrome-audit.mjs checks every admin state at 390 against this, and walks list, record, editor step and back counting the top bar controls.

### Gestures

All touch only, all with a visible equivalent (the row menu, a button, the top bar Back), none on a sideways scrolling area, all collapsed to no animation under Reduce motion (the finger is still followed).

- Edge Back (`src/shell/useEdgeBack.js`): a drag from the left 24px moves the screen with the finger over the screen it returns to (a static copy kept by nav-history.js at the push, shifted a third of the width), releases past 40 percent or with a flick through the same Back the top bar calls (a screen's leave guard still applies, and the screen springs back if the entry did not change), springs back below. Never at a section root, never with a dialog open.
- Sheets (`src/ui/Sheet.jsx`): the handle, the title and (scrolled to the top) the body follow the finger; release past a third of the height or with a flick dismisses. The screen behind scales back (`--v-recede` on `.lay-root`, 0.96 at most) and returns. Backdrop clicks in a sheet's first 400ms are ignored so a long press cannot close or press into its own sheet.
- Row swipe (`src/ui/SwipeRow.jsx`): leads (right Call, left Callback tomorrow at nine with an undo, `LeadSwipe`), planner posts (right Send for approval). Earlier, kept as they were: Next up (done, snooze), Triage (keep, bin, later), Lists (remove).
- Long press (`HoldRow`, `LeadSwipe`, `RowSheet`): a lead, client or project row opens its essentials and the row menu's actions; a tap still opens the record. The tap that follows a long press is swallowed.
- Docs: a doc row on All docs swipes right to pin and left to delete with Undo and a long press opens its sheet (SwipeRow, `onHold`, RowSheet); in the editor the grip on a block drags it (touch-action none on the grip only) and a tap on it opens the block menu, a swipe left on a block that is not being typed in deletes it with Undo (SwipeRow's `gate`), and edge Back saves first. Duplicate has no swipe (one action a side): it is in the sheet and the menu.
- scripts/gesture-test.mjs drives all of it with real touch events at 390.

### Empty states

Two components, never mixed: `EmptyState` (`data-state="empty"`, the first time: what this screen is for and one primary action) and `NoResults` (`data-state="no-results"`: names what was searched or filtered and offers one Clear). Every list screen has both; Deals and Projects are asserted by name. scripts/empty-audit.mjs checks copy, the action and its 44px height at 390.

## Crons and jobs

- reminders (once a day at 13:00 UTC on the Hobby plan, the morning digest; FIFTEEN_MINUTE_MODE keeps the per event path for the Pro plan): callbacks due today or overdue, meetings today, retainer bills due today, review asks three days after a release, and every task due today under Tasks; once each through sentReminderKeys; stamps health.crons.reminders (lastRunAt and the last twelve run times).
- Reminders for tasks (tasks with a due date): on every call, however often it comes, the same endpoint pushes "Task due: <label>" with "<business> · due <time>" and /?open=<leadId> (a project's task opens its client) for every live lead and project whose nextAction has remindAt in the past, notifiedAt empty and doneAt empty, and settings.notifications.reminders.tasks on, then stamps notifiedAt; notifiedAt is the key, so an outside scheduler pinging the endpoint every 15 minutes (docs/RUNBOOK.md) and the daily Vercel run overlap without a duplicate. Settings, Notifications reads the run times to say Every 15 minutes or Once a day at 9am.
- The New idea push is not a cron: api/planner.js sends it the moment a client's suggestion is written ("New idea from <client>", deep link /clients/:id/planner?ideas=1), unless settings.notifications.reminders.ideas is false; the New idea task on the client's Ideas checklist is written either way.
- daily (06:00 UTC): rolls retainer.nextBillAt, extends retainer schedules to six future months, cancels retainers past their notice, puts back stage client on any live record whose stage is not a stage but carries client evidence (api/_lib/pipeline.js: clientSince, a won outcome, a published showcase, a project, a purchase, a planner switched on, a testimonial; the nightly enricher has been seen to write stage as ''), counting each heal on the record (stageHeals) and naming it in health.crons.daily.healedRecords, which the notifications drawer shows as a System item ("X was restored to Clients", and after more than two heals, that something upstream is still wiping it), stamps clientSince on any client or won record missing it (the earliest of its first purchase, first project, or updatedAt; scripts/backfill-client-since.mjs runs the same rule on demand, report first), writes the health document.
- Outside this repo: the nightly enrichment scan and the scraper write straight into call_leads (enrichment{lastScanAt, scanCount}, sourceId); health reports when either is quiet for 36 hours.

## Known issues

- Sign out everywhere is not available: sessions carry no generation number (RUNBOOK covers rotating SESSION_SECRET).
- The Call Console keeps its own copy of the leads list and pings the shell on changes; two tabs can briefly disagree.
- Reads keep the last list and show an ErrorState with Retry when a fetch fails; writes roll back and toast.
- Offline writes are refused, not queued (Prompt 14 decision); the service worker serves the last GET of each list for reading.
- The marketing site still carries raw hex in its own pages and index.css; the hex count script tracks the total, and CLAUDE.md's standing rule is that it only ever goes down (90 after Site Prompt 6, down from 119 at 3.1.0 and 145 at 3.0.0: the maintenance screen rebuild took out the starfield's literals, and deleting the print shop took the last eighteen with it).
- No new vercel.json rewrite routes /clients/:slug to its prerendered static file; Vercel's documented routing order checks the output directory for a real file before the rewrites array, so it already wins once scripts/prerender-clients.mjs has written it, and there is no declarative "if the file exists" rewrite condition to express the non-prerendered fallback safely. See docs/RUNBOOK.md, "Prerender."
