# Planner v2: decisions

One line each: the milestone, the choice, why.

- 1.1: firstName reads `askFor` through the portal's own `portalFirstName`, and logoUrl reads `portalLogo` through safeUrl. The CRM has no `name` field; `askFor` is the one it shows as Contact, and the portal already reads it this way.
- 1.1: Rob's "posted" push names the post's day ("Kims Cafe posted the Dec 16 post"), not its title. A post's title is its caption's first line, and a push never carries a caption.
- 1.1: a caption or image change pushes one version per change request (only when the newest version is older than `clientNoteAt`). The editor autosaves every keystroke burst, and without this one request would fill all five slots with half-typed copies.
- 1.1: `reviewAt` is stamped when a post moves into review (its stored status was not review), not on every save of a post already there. The same reason: autosave resends the status.
- 1.1: `decidedAt` is stamped on posted too, as written. Part 2's "usually approves within" reads `approvedAt` first, then `decidedAt`, so a later Posted does not stretch the measure.
- 1.2: the planner borrows only `tokenStyles` (a string) from the admin kit and builds its own copies of Card, Pill, Button, SegmentedControl, Sheet and the glass TabBar in `src/components/planner/parts.jsx`. A public page should not pull the whole admin kit, and the prompt asks for a TabBar copy rather than an import.
- 1.2: the tab bar shows at every width (a centred pill, 360px at most on a computer). The planner has no sidebar to fall back on, unlike the CRM.
- 1.2: the portal's Back to your portal stays, as an icon button at the left of the top bar on the tab roots when the page was opened from the portal (an existing feature; the CRM pattern for Back is an icon at the left).
- 1.2: the marketing ClientFoot is dropped from the planner; the tab bar is the page's foot, as in the CRM. The dead link page keeps the email in its line.
- 1.2: focused screens are search params (`?review=1`, `?post=<id>`) pushed as real history entries with `state.pl`, so the phone's Back and the top bar's Back are one step; a cold open backs to its tab root. An old `?tab=posts` link opens Plan.
- 1.2: layers that mean the screen (tab bar, sheets, toast) portal to the body inside their own `.lay-root`, because `main.page-fade` animates a transform and fixed layers inside it would be fixed to it.
- 1.3: Ask for a change sends the reason's own words as the note when the client picks a reason and writes nothing (the door still requires a note, which is what Rob reads); Send needs a reason or a line.
- 1.3: Review takes its queue once when it opens, so an approval does not reshuffle the rest; a post that turned stale (not waiting any more) is passed over, since there is nothing left to answer, and only a failed call stays on screen with Retry.
- 1.3: Home's This week reads the loaded month only, so a week that runs into the next month shows no dots on those days. The read is per month and no new field is added.
- 1.3: the audits' Home without needs uses a second mock token (plnrCLEAR) that reads L11's month with review shown as approved, rather than a second planner client in the fixtures, which would change the admin screens' data.
- 1.4: the Feed shows the loaded month only: its posts still to go up, newest first, then up to six of its posted ones. Earlier months' posted posts are not in the read (one month per GET), and no second request was added.
- 1.4: below 400px the calendar lets its grid use the page gutter (4px from each edge) so seven columns stay 44px wide at 320.
- 1.4: the timeline's "You approved it" carries no date: the read has no decidedAt or approvedAt, and the prompt names no such field for it, so it renders without one. Posted uses postedAt, which the read does carry.
- 1.4: an ad's page shows the ad card (the Ads screen's, shared) instead of the Instagram preview, with no Copy card and no settled line; the client does not post ads.
- 1.4: Post it in 4 taps stays on screen, every step ticked, after I posted it, instead of vanishing the moment the post turns Posted.
- 1.5: the Ideas composer's one box is split for the door: its first line (120 characters) is the subject Rob reads as the title, the whole text is the details when it is longer. The old Add a link field is dropped; the prompt's composer has none, and a link can go in the text.
- 1.5: Add photos shows only when uploads are configured (the Cloudinary variables), as the old sheet did with its photos.
- 1.5: "In the plan for Dec 16" renders as "In the plan." The read carries no date for an idea's post and the prompt names no such field.
- 1.5: the Ads screen keeps the month arrows, like Plan, because the read is one month.
- 1.6: the full feel audit (both themes, both motions, every admin screen) was stopped after its first hundred rows: run beside the full layout audit it would take most of a day, and part 1 changes no admin screen (the client planner is a marketing page, which the feel audit skips). Its partial run showed GAP rows only on screens this job does not touch (Analytics, Call Console, Triage, Deals, Clients); those ids are re-run alone against this build and the base commit before the final report. The full feel run happens once, at 3.4; parts 1 and 2 run it on the planner's own states.
- 1.6: the five width layout audit ran whole at 320 and 390 and through most of 430 (842 rows, no failure) before its time limit; the rest of 430, 768 and 1280 were run for the marketing pages (the public planner is the only thing part 1 changed); 768 and 1280 for the admin screens ran in the first 204 rows of a second pass with no failure and are run in full at the end of part 2, which is the part that changes the admin.
- 2.1: the batch send moves posts only (kind post), as the prompt says "every Making post"; an ad still goes for approval one at a time. Undo uses the posts PATCH per id (the prompt adds one route action, for the send).
- 2.1: opening an idea is stamped on the server: the suggestions PATCH takes `seenAt: true` and writes the time itself.
- 2.2 to 2.4: the board, the composer and the batch send landed in one commit: all three live in AdminPlanner.jsx and AdminApp.jsx, and splitting a file's hunks across commits by hand would risk a commit that does not build.
- 2.2: "usually approves within" reads the posts the shell holds (this month and next); older months are not loaded on this screen and no new request was added. It is hidden under three decided posts.
- 2.2: on a phone the Calendar view is the month's days with something on them, in order, each item a chip; seven columns of chips do not fit 390.
- 2.2: a phone board card keeps its menu beside the long press, so the gesture has a visible equivalent (the CRM's rule).
- 2.2: a drag lives on the whole card; a press on a card's picture or icon counts as the card (an SVG or an image under the pointer would not start the drag), and the drag source is kept in a ref so a quick drag is not lost before React stores it.
- 2.3: the phone editor is /clients/:id/planner/:postId; its skeleton is one form card where the editor's first block sits (the form's length depends on the post, unknown until it loads).
- 2.3: the board's moves are drafted like any edit and autosave writes them; Mark posted from Rob writes postedBy rob.
- 2.4: on a phone the top bar carries one declared action (the chrome rule): Send n for approval when something is ready, else New post; New post, Copy across, Add ad and Add reel are in the month's menu.
- 2.4: the Ideas rows of the audit screens use the page as their region at every width: Ideas is a view of the planner page now, not a card beside the month.
- 3.2: client quiet hours are 9 PM to 8 AM New York: the client has no setting of their own. A push that falls there is not sent and not queued (Rob's own quiet rule); its keys stay unseen, so the next send carries them. No sweep sends review pushes later: on the first deploy a sweep would ping every client about everything already waiting.
- 3.2: Post today never names the post: "Your post goes up today" (or "2 posts go up today"), because a post's title is its caption's first line and a push never carries a caption. It runs from 9:00 to noon New York and stamps the day either way, so a cron that missed the morning never sends at teatime.
- 3.2: "Rob answered your idea: <subject>" carries the client's own subject (their words, not a caption), never Rob's note.
- 3.2: the whole month approved means every live item of the month is past review (approved, posted, live or finished), stamped in planner.approvedMonths (24 kept) before Rob's push goes.
- 3.2: the route hooks read a swappable clock in plannerPush.js so a test can pin the hour; quiet hours depend on it.
- 3.3: the three switches show whether or not this device is on: they live on the client's record, so a second device follows them, and they can be set before turning a device on. An iPhone that has not added the planner to its Home Screen gets the hint instead of a Turn on button that cannot work there.
- 3.3: the Next up loop looks for an open task carrying the post's id and ticks it through the shared task rules; no task carries one today (the task schema has no such field and nothing writes one), so with none nothing is written, as the prompt says.
- 3.3: Rob's Setup line reads the device count the planner or the portal wrote last (they share the devices) and says Alerts on only when a device exists and a switch is on.
- 2.5: Preview as <client> in the editor's foot shrinks and ends in an ellipsis: with a long client name it ran past a phone's screen (preship's layout audit found it).
- 3.4: the board's four columns show from 1024 up, as the Deals board does; under that (a tablet, a narrow window) it is the chip row and one column. The layout audit at 768 found the columns running past the screen.
- 3.4: the feel audit's GAP rows outside the planner (Analytics, the Call Console, Leads, Triage, Fill from filters, Deals, Clients, Projects, Settings, Drafts) were checked against the base commit 50174e0 built on its own: the same rows fail there with the same numbers, so they come from before this job and are left alone.
